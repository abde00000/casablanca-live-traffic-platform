# Casablanca Live Traffic Intelligence Platform

An original, data-backed mobility analytics project for collecting **real traffic observations** in Casablanca and processing them through Kafka, Spark Structured Streaming, Delta Lake, Hive Metastore, and SQL.

**There is no synthetic traffic generator, sample-data fallback, or fabricated traffic feed in the runtime.** The collector requires a TomTom API key and publishes only successful Traffic Flow API responses. If the key or API is unavailable, collection stops or reports an error; it does not invent measurements.

## Research question

How do provider-observed road speeds and travel-time delays vary by hour and across Casablanca's arrondissements, based on a consistent sample of road locations?

The first configuration samples one named road point in each of 16 Casablanca arrondissements. It is a **sample of locations**, not a measurement of every road or an official district-wide traffic statistic.

## Data source and access

The collector uses TomTom's Traffic Flow Segment Data API. TomTom documents Morocco traffic coverage and a free allowance of 20,000 monthly segment-data requests; check your account and the current pricing/terms before use. Each response can include current and free-flow speeds, travel times, confidence, road class, closure status, and segment coordinates:

- [TomTom traffic market coverage](https://developer.tomtom.com/traffic-api/documentation/product-information/market-coverage)
- [TomTom pricing](https://docs.tomtom.com/pricing)
- [Flow Segment Data API fields and request format](https://developer.tomtom.com/traffic-api/documentation/tomtom-maps/traffic-flow/flow-segment-data)

TomTom's pricing documentation also notes that some APIs on its older Maps platform are being superseded by Orbis APIs. The endpoint is configurable in `.env`; verify that Flow Segment Data is enabled for your key and remains supported for your intended use before starting collection.

The location catalogue is derived from named roads and administrative arrondissement relations in OpenStreetMap (OSM). It records OSM way/relation IDs and the query snapshot time. Attribution: **© OpenStreetMap contributors, ODbL**. See [OpenStreetMap copyright and licence](https://www.openstreetmap.org/copyright).

The API key is private: put it in `.env`, never commit it, and never paste it into a public report or source file. `event_id` is only a technical identifier for Kafka; the speed and travel-time measurements are never generated by this project. `STORE_RAW_PROVIDER_RESPONSE=false` omits the full provider JSON by default, but the normalized speed/travel-time fields are still real provider data and are persisted in Kafka/Delta. Before archiving, redistributing, or publishing any provider values, review the current TomTom developer terms for your account. Do not publish provider data unless the terms permit it.

## Sampling plan and quota

The default cadence is one poll per hour at 16 configured points: approximately **11,520 calls in a 30-day month**, before retries. The collector also enforces a configurable local monthly request budget (18,000 by default) to leave headroom below the currently listed 20,000 monthly allowance. Confirm the current allowance before starting; do not increase the polling rate without checking it.

`collected_at_utc` is the time this project made the API request. It is not claimed to be the timestamp of an underlying vehicle probe. TomTom's returned values are provider-derived traffic estimates, not direct measurements from sensors installed by this project.

## Architecture

```text
TomTom Flow Segment API
        │  real response only; no synthetic fallback
        ▼
Python collector ──► Kafka: traffic-flow-raw
                           │
                           ▼
                   Spark Structured Streaming
                    ├── Bronze: raw Kafka JSON + metadata
                    ├── Silver: parsed/validated metrics + rejects
                    └── Gold: hourly arrondissement/location aggregates
                           │
                           ▼
             Delta Lake paths + Hive Metastore (PostgreSQL)
                           │
                           ▼
                  Spark SQL tables and views
```

- **Collector:** polls the fixed, provenance-tagged OSM location catalogue, applies a local API-call budget, and publishes provider responses with collection metadata.
- **Bronze:** preserves the Kafka JSON value, key, timestamp, topic, partition, and offset.
- **Silver:** validates response fields and timestamps, retains invalid payloads with explicit reasons, and derives speed ratio, travel-time index, delay seconds, and delay percentage. It deduplicates by event ID within a two-hour event-time watermark.
- **Gold:** calculates hourly averages and counts by location/arrondissement, including average confidence and provider-reported closure observations. The optional analyst delay bands are `LOW_DELAY` (index ≤ 1.10), `MODERATE_DELAY` (> 1.10–1.25), `HIGH_DELAY` (> 1.25–1.50), and `VERY_HIGH_DELAY` (> 1.50). These are transparent project thresholds, not official traffic classifications; the continuous travel-time index remains the primary measure.
- **Catalog:** PostgreSQL persists Hive Metastore metadata; Spark SQL registers Delta locations and analyst views.

## Start-up

1. Create a TomTom developer account/key with access to Traffic Flow Segment Data. **Do not send the key in chat.**
2. Copy `.env.example` to `.env`, insert the key locally, and set a strong local-only PostgreSQL password.
3. Read `commands.txt`, then start the Compose services and create the Kafka topic.
4. Start Bronze, Silver, and Gold in separate terminals. Only then start the collector with the `live` Compose profile.
5. After the first API observations reach Delta, run the SQL registration script and query the views.

If the API key is missing/invalid, Kafka is unavailable, or the request budget is exhausted, the collector will not create placeholder traffic observations. API-dependent collection cannot be verified until you configure your own key.

## Validation and limitations

Standard-library unit tests validate the OSM location catalogue and local monthly request budget; they do not create traffic records. Python syntax and Compose configuration can be checked without credentials. A live API smoke test and full Docker/Spark/Kafka integration run require Docker, network access, a valid TomTom key, and quota availability.

The sample covers one point per arrondissement and one road point does not represent all roads in that arrondissement. Road names and boundaries are OSM community data, not a municipal traffic inventory. Provider confidence and coverage may vary by location and time. The live collection begins only after deployment, so the project builds its own history over time; it does not claim access to a historical archive through the free real-time endpoint.
